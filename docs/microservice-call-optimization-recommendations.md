# 微服务间调用优化方案

## 1. 当前架构边界

当前架构已经具备以下能力：

- 使用 etcd 进行服务注册与发现；
- 使用 gRPC 进行主要的微服务间调用；
- 使用 `round_robin` 在同一服务的多个实例之间分配请求；
- Gateway 是 HTTP 主入口，负责认证、HTTP 路由、参数校验和协议转换；
- Gate Server 是 WebSocket 主入口，负责长连接生命周期、连接管理和长连接业务请求；
- Gateway 和 Gate Server 都会部署多个实例；
- 微服务之间也可能互相调用，而不只是被 Gateway 调用。

因此，当前最需要补齐的不是重新设计服务调用方式，而是调用治理和故障隔离能力。

## 2. 推荐目标架构

```text
HTTP Client                         WebSocket Client
    |                                      |
    v                                      v
Gateway-1 / Gateway-2 ...          Gate-1 / Gate-2 ...
    |                                      |
    +---------------+----------------------+
                    |
       gRPC + 超时 + 熔断 + Trace
                    |
              服务发现（etcd）
                    |
       +------------+------------+
       v                         v
  User / Item / Computing    其他微服务

Gate Server 集群还需要共享连接路由表和消息总线，不能只依赖实例本地内存。
```

推荐先保留现有的 `etcd + gRPC round_robin`，待服务数量和治理复杂度上升后，再引入 Envoy 或服务网格。

## 3. 优化方案

### 3.1 建立服务依赖矩阵

建议维护一份版本化的依赖矩阵：

| 调用方 | 被调用方 | RPC 方法 | 超时 | 是否幂等 | 是否允许重试 | 降级方式 |
|---|---|---|---:|---|---|---|
| Gateway | User | Login | 待压测 | 否 | 否 | 返回明确错误 |
| Gateway | Item | 查询接口 | 待压测 | 是 | 最多 1 次 | 返回缓存或失败 |
| Gateway | Computing | 计算接口 | 待压测 | 视业务而定 | 谨慎 | 返回默认结果 |

依赖矩阵可以帮助团队明确调用责任、超时预算、重试边界和故障降级方式。

同步调用链建议控制在 3 层以内，避免出现 `Gateway -> A -> B -> C -> D` 或 `Gate -> A -> B -> C`。同时禁止循环依赖，例如 `A -> B -> A`。

Gateway 和 Gate Server 应保持入口层职责，不应集中承载所有领域业务逻辑。

### 3.2 设置分层超时和 Deadline

不要直接无限期沿用入口请求的 Context。建议为每次下游调用设置明确的 Deadline：

```text
HTTP 请求总预算：3s
  Gateway 处理：200ms
  gRPC 下游调用：1s
  数据库操作：500ms
```

示例：

```go
ctx, cancel := context.WithTimeout(ctx, 1*time.Second)
defer cancel()

resp, err := userClient.Login(ctx, req)
```

具体数值应根据 P95/P99 延迟和压测结果调整。下游超时必须小于上游剩余预算。

### 3.3 只对幂等请求进行有限重试

适合重试的请求包括查询、读取配置和明确幂等的更新操作。登录状态写入、创建订单、扣库存、扣款等有副作用的操作，在没有幂等键之前不应自动重试。

推荐策略：

- 最多重试 1～2 次；
- 使用指数退避和随机抖动；
- 重试总时间不能超过原始 Deadline；
- 记录重试次数，防止故障期间流量被放大。

### 3.4 增加限流、并发隔离和熔断

应按“调用方 -> 被调用方”分别配置保护策略：

- 最大并发数；
- 有界等待队列；
- 单请求超时；
- 连续失败熔断；
- 半开探测；
- 快速失败或降级响应。

Gateway 入口还应支持按 IP、用户和接口限流。过载时返回 `429` 或 `503`，不要无限排队。

### 3.5 改善服务发现和实例摘除

现有 etcd 服务发现可以继续使用，但建议补充以下规则：

1. 服务监听成功且依赖就绪后再注册；
2. Readiness 失败时停止接收新请求；
3. 停止流程先摘除实例，再等待在途请求完成；
4. etcd Watch 中断时保留已建立连接，并支持恢复后重新同步；
5. 对实例数量、租约续期失败和地址变更增加监控。

`round_robin` 只负责实例选择，不负责超时、熔断和故障重试。

对于微服务互相调用的场景，每个服务都应使用统一的服务发现客户端和调用治理组件。调用方应按被调用服务维护独立的连接池、超时、并发上限和熔断状态。

### 3.6 Gateway 多实例策略

Gateway 多实例应尽量保持无状态：

- 不在本地保存必须跨请求共享的会话状态；
- 认证状态放在 Token 或共享存储中；
- 不依赖固定实例处理后续 HTTP 请求；
- 通过 readiness 和优雅退出完成滚动发布；
- 对不同下游服务分别设置并发上限，避免一个服务拖垮全部 Gateway。

### 3.7 Gate Server 多实例策略

多个 Gate Server 只能解决接入容量问题，不能自动解决跨实例推送。建议增加：

1. Redis 等共享连接注册表：`user_id/session_id -> gate_instance_id`，并设置 TTL；
2. Gate 实例心跳和异常过期清理；
3. Redis Streams、NATS 等消息总线，将目标消息投递到连接所在实例；
4. 本地内存只保存实际 WebSocket 连接，不让业务服务直接访问；
5. 客户端断线重连、消息去重和必要的顺序保证；
6. 发布时停止新连接、通知客户端重连，并等待宽限期退出。

业务服务应发布业务事件，由 Gate Server 负责查找连接和协议编码，而不是直接调用某个 Gate 实例。

### 3.8 何时引入 Envoy

Envoy 可以统一提供：

- gRPC/HTTP 负载均衡；
- 超时和有限重试；
- 熔断和连接池；
- mTLS；
- 灰度发布；
- 访问日志、指标和 Trace。

但 Envoy 不会自动理解当前 etcd 中的自定义实例数据格式。若要使用 Envoy，需要：

- 通过 Kubernetes Service/DNS 提供服务发现；或
- 建设将 etcd 数据转换为 Envoy xDS/EDS 的控制面；或
- 使用 Istio、Consul Connect 等服务网格。

推荐演进路线：

```text
第一阶段：etcd + gRPC round_robin + 应用级调用治理
第二阶段：Kubernetes Service + Envoy
第三阶段：服务数量和治理需求较大时引入 Istio 等服务网格
```

### 3.7 完善可观测性

建议补充 Prometheus 指标，并按服务和接口统计：

- 请求总数和错误率；
- P50/P95/P99 延迟；
- 超时、重试和熔断次数；
- 当前并发数；
- 每个实例的请求量和失败率；
- etcd 注册、续租和 Watch 异常。

Trace 和日志中禁止记录密码、Token、完整请求体以及带真实参数的 SQL。高基数字段如 `trace_id`、`request_id`、用户 ID 不应作为 Prometheus 标签。

### 3.8 将非实时工作异步化

日志、审计、统计、通知、推荐计算和批处理等工作不应全部放在同步调用链中。可以使用 Redis Streams、NATS、Kafka 等消息系统：

```text
Gateway -> 核心业务服务
       └-> 发布事件 -> 消息系统 -> 通知/审计/统计服务
```

这样可以减少同步链路长度，并降低级联故障风险。

### 3.9 提升 Kubernetes 高可用能力

在增加副本前，先补充：

- `startupProbe`、`readinessProbe`、`livenessProbe`；
- CPU/内存 requests 和 limits；
- 优雅退出和 RollingUpdate；
- PodDisruptionBudget；
- 多副本和跨节点调度；
- 接入指标后的 HPA。

不要在没有 Ready 检查和优雅摘除的情况下直接把所有服务改成 3 副本。

## 4. 推荐实施顺序

### 第一阶段：优先完成

1. 为 Gateway、Gate Server 以及所有服务间 RPC 增加明确超时；
2. 建立包含服务间调用的依赖矩阵；
3. 对幂等查询增加有限重试；
4. 增加超时、错误率和调用延迟指标；
5. 增加健康检查和优雅停止；
6. 确认 etcd 实例摘除和重新发现正常；
7. 先实现 Gate 的连接注册表和消息总线。

### 第二阶段：稳定性治理

1. 增加并发隔离和熔断；
2. 增加 Gateway 入口限流；
3. 为热点查询增加缓存；
4. 将通知、审计和统计改为异步；
5. 为无状态服务增加多副本、PDB 和 HPA。

### 第三阶段：统一流量治理

在需要统一 mTLS、灰度发布、跨语言调用策略或复杂流量治理时，再引入 Envoy 或 Istio。

## 5. 结论

当前架构不需要立即替换 gRPC 客户端负载均衡。最优先的工作是补齐 Gateway、Gate Server 和微服务之间的超时、重试边界、熔断、限流、可观测性和优雅摘除。Envoy 可以作为后续统一治理层，但不能替代服务依赖设计、幂等设计、服务发现控制面，也不能自动解决 Gate Server 的跨实例 WebSocket 消息路由问题。
