# 订单、支付与秒杀场景及当前设计审查

> 审查范围：`order`、`pay`、`promotion` 及其 Kafka 事件契约。  
> 假设：进程和基础设施总体可用，不讨论机器崩溃；但正常运行中的并发、网络延迟、超时、重复请求、重复/延迟消息、用户重复操作和第三方支付异步回调仍然会发生。  
> 审查日期：2026-09-06。

## 1. 当前链路概览

```text
用户秒杀
  -> promotion Redis Lua 原子扣库存、累计个人购买数
  -> Kafka: promotion_order_create
  -> order 创建 PENDING_PAY 订单，并写 Redis ZSET（15 分钟超时）
  -> pay 创建支付单/支付流水
  -> 第三方异步回调 pay
  -> pay 本地事务置 SUCCESS
  -> Kafka: pay_report(PAID)
  -> order 从 PENDING_PAY 条件更新为 PAID

订单超时/取消
  -> order 从 PENDING_PAY 条件更新为 CLOSED/CANCELLED
  -> Kafka: promotion_order_compensate
  -> promotion Lua 幂等恢复库存和个人限购数

支付晚于关单
  -> order 收到 PAID，发现订单已 CLOSED/CANCELLED
  -> Kafka: refund_report
  -> pay 创建退款任务并轮询执行
```

已有的正确设计包括：Redis Lua 原子扣减；订单状态的条件更新；支付本地表事务；Kafka 消费后提交 offset；订单创建以 `request_id` 去重；库存补偿以 `request_id` 幂等；退款单以 `refund_no` 去重；关单后收到成功支付会转退款。

## 2. 用户可能遇到的购买与支付情况

### 2.1 抢购与下单阶段

| 场景 | 用户表现 | 正确业务结果 | 当前项目表现/风险 |
|---|---|---|---|
| 活动未开始、已结束、被冻结 | 无法购买 | 明确提示活动不可用 | `Seckill` 本身未查活动时间和状态，仅依赖库存 key 是否存在；旧 key、错误 TTL 或人为预热错误时可能仍可买 |
| 商品库存未加载 | 点击后失败 | 提示活动未准备好，可重试 | Lua 返回 `-1`，已覆盖 |
| 库存不足 | 抢购失败 | 不生成订单、不扣库存 | Lua 原子判断，已覆盖 |
| 超过个人限购 | 抢购失败 | 不生成订单、不多扣库存 | Lua 原子判断，已覆盖 |
| 同一用户并发抢购 | 部分成功或全部受限 | 总购买数不超过限额 | 单 Redis key 下 Lua 原子执行，已基本覆盖 |
| 用户连续点击/客户端超时重试，复用同一 `request_id` | 可能收到多个“成功”响应 | 只能扣一次库存、只建一个订单 | **未覆盖**：扣库存 Lua 不使用 `request_id` 幂等；同一请求重放会再次扣库存并增加限购数，order 虽只建一单，但多扣部分不会自动补回 |
| 客户端重试但未复用 `request_id` | 多次抢中 | 受限购规则约束；无单件限购时可产生多单 | 属于业务策略问题；需要客户端幂等键和服务端防重窗口共同约束 |
| 扣库存成功，订单消息发送失败 | 用户看到失败 | 库存和限购恢复，允许重试 | 尝试同步 Lua 补偿；但补偿没有幂等 key，若生产端实际已写入而因应答超时报错，可能一边恢复库存、一边仍创建订单，造成超卖 |
| 消息发送成功但响应丢失 | 用户看到超时/失败，稍后却有订单 | 可按 `request_id` 查询结果，重复请求返回原结果 | 当前响应只有 `success`，没有订单号/处理中状态，也没有查询接口；用户容易重复购买 |
| 创建订单消息重复投递 | 用户应只得到一单 | 同一 `request_id` 只创建一单 | 应用层先 Count 再 Insert，依赖数据库唯一约束兜底；仓库没有完整建表 DDL，无法确认 `orders.request_id` 唯一。并发消费时“先查后插”本身不原子 |
| 消息在队列积压超过 15 分钟才被消费 | 订单刚出现就过期 | 一般应从订单创建/用户可见时开始计时，或直接拒绝陈旧事件并补库存 | 当前超时点为事件产生时间 `event.CreatedAt + 15m`，因此订单可能一创建即关闭；这是可选策略，但前端必须明确，且应监控消息年龄 |
| 订单插入成功，写超时 ZSET 失败 | 订单一直待支付 | 后台仍能根据 DB 截止时间关单 | **遗漏**：DB 没有明确 `expire_at`，扫描只依赖 Redis ZSET；消息重投有机会修复，但若消费流程退出或消息处理策略异常，可能永久不过期 |
| 订单创建失败 | 用户无订单 | 恢复库存和限购 | 会发补偿消息，方向正确；但 DB 写入与补偿事件不是事务/outbox，发布失败会漏补 |
| 客户端伪造秒杀价格/币种 | 极低价下单 | 服务端使用活动配置中的价格和币种 | **严重遗漏**：`SeckillReq.price/currency_type` 直接进入建单事件，Lua 中虽保存了价格却未读取校验 |

### 2.2 待支付与创建支付阶段

| 场景 | 用户表现 | 正确业务结果 | 当前项目表现/风险 |
|---|---|---|---|
| 正常创建支付 | 获得支付流水 | 金额、用户、币种均来自可信订单快照 | `CreatePayment` 查订单金额，但未校验订单状态、当前用户、订单是否过期；币种取客户端参数而不是校验订单币种 |
| 对已关闭/已取消订单创建支付 | 仍可能跳转支付 | 拒绝并提示订单已关闭 | **遗漏**：`CreatePayment/CreateTransaction` 不检查业务订单状态，可为 CLOSED/CANCELLED 订单创建支付单 |
| A 用户拿 B 用户订单号创建支付 | 可能替他人付款或探测订单 | 按产品策略显式支持“代付”，否则拒绝 | **遗漏**：`CreatePayment` 没有鉴权/归属校验；`CreateTransaction` 更信任传入的 `user_id/amount` |
| 调用方直接传低金额创建流水 | 少付 | pay 服务再次读取并核对订单金额 | **严重遗漏**：公开 RPC `CreateTransaction` 直接相信请求金额、用户和币种，没有与订单核对 |
| 相同支付请求重复提交 | 返回同一流水 | 幂等返回 | 相同 `request_id` 会产生稳定流水号并校验部分参数，已基本覆盖；但没有校验 currency/user，参数冲突检测不完整 |
| 同一订单用不同 `request_id`/渠道重复发起 | 用户切换支付方式 | 可存在多流水，但最多一个成功，其余应主动关停/退款 | payment order 锁能串行创建，但首条流水后仍可创建新流水；成功后后续创建会拒绝。已经存在的其他 PENDING 流水不会被关闭 |
| 免费商品/零元秒杀 | 无需第三方支付 | 直接置已支付/完成 | `CreateTransaction` 要求金额大于 0；当前没有零元订单专用流程 |
| 金额精度问题 | 显示或支付差 1 分 | 全链路使用整数分 | 秒杀订单以整数计算，但 pay `CreatePayment` 从 DB `float64` 读金额再 round；建议 DB DECIMAL + 代码整数分，避免精度和单位混淆 |

### 2.3 支付中、回调与订单超时竞态

以下以数据库条件更新的先后顺序定义最终结果，而不是以用户点击支付按钮的时刻定义。

| 时序/竞态 | 正确最终结果 | 当前设计结论 |
|---|---|---|
| 支付成功回调先到，订单超时扫描后到 | 订单 PAID，不释放库存 | pay report 先将 PENDING_PAY -> PAID；超时更新影响 0 行，基本正确 |
| 超时扫描先把订单置 CLOSED，支付成功后到 | 订单保持 CLOSED，钱原路退回，库存释放 | pay report 会发退款事件，方向正确 |
| 支付成功和超时“同一瞬间” | 只能有一个状态抢占成功；支付若未抢到则退款 | 两边都用 `WHERE status=PENDING_PAY` 条件更新，状态不会同时成功；已覆盖核心竞态 |
| pay 已收到成功回调，但 `pay_report` 尚未送达，order 先超时 | 关单、释放库存，随后自动退款 | 当前按此处理；用户会短暂看到“支付成功但订单关闭/退款中”，前端需展示中间态并通知退款 |
| 第三方扣款成功，但成功回调长时间未到 | 订单超时；之后回调触发退款 | 最终可退款，但依赖第三方最终回调；缺少主动支付结果查询/对账，回调永久缺失时无法发现 |
| 第三方回调重复 | 幂等，不重复记账或通知 | 本地状态相同则 no-op，但每次仍再次发布相同 pay report；下游 PAID 幂等，迟到支付退款单号稳定，基本安全 |
| 第三方先回调 FAILED，后回调 SUCCESS | 以第三方真实终态为准，或人工异常处理 | **遗漏**：第一次 FAILED 后流水变终态，后续 SUCCESS 被 `FailedPrecondition` 拒绝；且 FAILED 不向 order 报告，订单只能等超时 |
| 用户取消支付与成功回调并发 | 若实际扣款成功则必须退款；不能只拒绝回调 | 行锁保证仅一方先更新，但取消先赢后，成功回调会被拒绝，**没有按第三方交易号建异常退款/对账任务，存在已扣款未退款风险** |
| 用户取消订单，但第三方支付页面仍可付款 | 晚到成功自动退款 | order 侧能转退款，但 CancelOrder 没有联动关闭 pay/第三方流水；增加晚支付概率 |
| 用户支付后立即查询订单 | 可能仍显示待支付 | 接受异步最终一致，提供“支付确认中”并主动查询 | 当前订单只有 PENDING_PAY/PAID/CLOSED/CANCELLED，没有 PAYING/确认中，也未看到聚合查询接口 |
| 订单已 PAID 后重复取消/超时 | 保持 PAID | 条件更新会拒绝/影响 0 行，正确 |
| 订单 CLOSED 后管理端强制改 PAID | 不应直接改；需要退款或异常审核 | RPC 只允许从 PENDING_PAY 转换，基本正确 |

### 2.4 退款与售后阶段

| 场景 | 正确业务结果 | 当前项目表现/风险 |
|---|---|---|
| 关闭订单收到迟到成功支付 | 创建唯一退款任务 | 使用 `R + transactionNo`，数据库重复键去重，已覆盖单流水重复消息 |
| 同一订单多条流水均成功 | 每笔实收分别退款，只保留业务允许的一笔 | 每条交易退款号不同，理论上可分别退；但 payment order 只允许首次从 WAIT_PAY 更新 SUCCESS，其他成功流水的本地状态与订单状态可能不一致，缺少专项处理 |
| 退款事件重复 | 不重复退款 | 插入唯一退款记录可去重，前提是表上确有唯一约束；仓库无完整 DDL 可验证 |
| 退款请求已被第三方受理，但本地调用超时 | 查询后确认，不盲目重复退款 | 任务先 `QueryRefund` 再 `Refund`，思路正确；第三方必须使用 `refund_no` 幂等 |
| 退款成功 | 用户收到退款，系统展示成功 | **当前实际未完成**：启动时使用 `MockGateway`，`Refund` 永远失败，所有退款会永久 RUNNING 重试 |
| 退款永久失败 | 告警并进入人工处理 | 当前无限重试，没有最大次数、死信/人工工单和明确告警升级策略 |
| 第三方查询返回 FAILED | 区分“可重试失败”和“终态失败” | 当前 QueryRunning/QueryFailed/查询报错都进入再次 Refund，缺少错误分类与退避策略 |
| 部分退款、多次退款、退款金额超过实付 | 严格校验累计退款额 | 当前仅消费事件金额，未校验支付单状态、实付金额、累计已退金额和币种 |
| 退款成功后库存处理 | 库存只恢复一次 | 库存是在关单时补偿，与退款结果解耦，符合秒杀释放策略；补偿 Lua 有幂等保护 |

## 3. 当前实现的关键遗漏

### P0：可能造成资金损失、低价购买或永久不一致

1. **价格和币种不可信**：promotion 直接信任客户端的 `price/currency_type`；pay 的 `CreateTransaction` 又可直接信任调用方的金额和用户。应由 order/promotion 服务端读取活动快照，pay 只接受 `order_no` 并服务端核价。
2. **支付成功与事件发布不是原子操作**：pay 提交 SUCCESS 后才直接发 Kafka。若发布失败且第三方不再重试回调，订单会超时并释放库存，而系统不知道需要退款。应使用本地事务 outbox（支付状态和待发布事件同事务），后台持续投递。
3. **订单终态与补偿事件不是原子操作**：order 先 CLOSED/CANCELLED 再发 Kafka。发布失败时库存不会恢复；而 RPC 会返回失败，重试虽然可能再次发布，但不能保证调用方重试。也应使用 order outbox。
4. **抢购请求本身不幂等**：Lua 扣库存前没有记录 `request_id`；网络重试可重复扣库存。同一个 Lua 中应检查/写入抢购幂等 key，并返回第一次结果。
5. **Kafka 写入“结果未知”时同步反向补偿不安全**：写请求可能已被 broker 接收但客户端超时。此时立即加回库存会与仍在队列中的建单事件并存，造成超卖。需采用可靠消息/outbox、事务消息，或让事件携带 reservation 并由状态机确认/取消。
6. **真实退款能力尚未接入**：`MockGateway.Refund` 固定失败，迟到支付目前无法完成退款。
7. **取消与成功回调竞态可能漏退款**：交易先被置 CANCELED 后，真实 SUCCESS 回调被拒绝。必须以第三方事实为准，将其记录为“取消后支付成功”并生成退款，而不是仅返回前置条件失败。

### P1：高概率导致订单、库存或体验异常

1. **过期订单仍可创建支付**：pay 不校验业务订单为 PENDING_PAY，也不校验截止时间。
2. **缺少订单归属鉴权**：持有订单号即可尝试创建支付；是否允许代付需要显式产品规则。
3. **超时只依赖 Redis ZSET**：缺少 DB `expire_at` 真相源和补扫任务。Redis key 丢失、写入失败或数据被清理会形成永久待支付订单。
4. **所有消费者遇一条毒消息/持续业务错误就退出**：公共 Consumer 的 handler 返回 error 会结束整个 Run；启动 goroutine 只记录日志，不重启。单条坏消息可使该 topic 后续所有正常消息停止消费，进程却仍在运行。
5. **缺少主动支付查询与日终对账**：只依赖异步回调，无法处理回调永久丢失、渠道与本地状态不一致、渠道重复扣款。
6. **订单创建幂等依赖未确认的 DB 约束**：`Count -> Insert` 有竞态，必须有 `UNIQUE(request_id)` 并以唯一冲突后读取作为正常分支。
7. **支付单的多流水状态收敛不完整**：一个支付单允许产生多条待支付流水，某条成功后其他流水未关闭；若它们也成功，缺少重复支付退款状态机。
8. **支付失败不通知订单**：订单仍保持待支付直至 15 分钟到期。允许重试可以接受，但应有明确策略；若不可重试则应立即关单。

### P2：可维护性、审计与用户体验问题

1. 订单没有 `PAYING/REFUNDING/REFUNDED/PAY_EXCEPTION` 等可展示状态；建议业务订单状态与支付/退款状态分离，并由聚合查询接口返回组合视图。
2. Kafka 事件虽有 `event_id`，多数消费者没有通用 inbox/event-log；当前幂等散落在业务字段和 Redis key 中，不利于审计。
3. 超时任务固定每秒最多处理 100 条且没有循环翻页；积压时吞吐约 100/s，应提供指标并在一次 tick 内分批清空到上限。
4. 超时扫描读取更新前的 `order.Status` 决定是否补偿，逻辑虽依靠补偿幂等容忍重放，但表达容易误判；应以本次 CAS 结果及持久化 outbox 为准。
5. 退款无限固定间隔重试，缺少指数退避、最大次数、错误分级、人工队列和 SLA 告警。
6. 仓库缺完整数据库 DDL，无法确认下列必要唯一约束：`orders(order_no)`、`orders(request_id)`、`payment_order(order_no/payment_no)`、`payment_transaction(transaction_no)`、`payment_refund(refund_no)`。

## 4. 建议的目标状态机

### 业务订单

```text
PENDING_PAY --支付确认--> PAID
     |                    |
     +--主动取消--------> CANCELLED
     +--到期------------> CLOSED

CANCELLED/CLOSED --发现渠道实收--> REFUNDING --> REFUNDED
                                  \-> REFUND_FAILED（人工处理）
```

订单的 PAID 与 CLOSED/CANCELLED 继续使用数据库 CAS 竞争；失败的一方必须产生持久化的后续动作。不要依赖“更新 DB 后立即发 Kafka”来保证后续动作一定发生。

### 支付流水

```text
CREATED -> PROCESSING -> SUCCESS
                    \-> FAILED
                    \-> CLOSED
CLOSED/FAILED --渠道确认实际成功--> LATE_SUCCESS -> REFUNDING
```

渠道回调是外部资金事实，不能因为本地状态已经 CLOSED/FAILED 就简单拒绝；应验签、去重、完整落库，再由规则决定支付成功入账还是退款。

## 5. 推荐整改顺序

1. 立即禁止客户端决定价格：promotion 从 Redis/DB 活动快照取价，order 保存不可变商品/活动快照；pay 只根据订单服务端数据建支付。
2. 为 pay、order 引入 transactional outbox；消费者引入 inbox/业务唯一键，并让单条毒消息进入重试/DLQ，不能退出整个消费循环。
3. 给秒杀 Lua 加 `request_id` reservation key，把扣库存、限购累计、请求幂等放在一次 Lua 中；重新设计 Kafka 发送结果未知时的确认/取消流程。
4. 接入真实退款网关，支持渠道幂等号、主动查询、指数退避、退款终态、人工兜底和告警。
5. 增加 DB `expire_at`，以 DB 为最终真相；Redis ZSET 只做加速，并定期从 DB 补建/补扫超时索引。
6. 完善取消后成功、先失败后成功、同单多流水成功、回调丢失等异常支付状态机，并增加渠道对账任务。
7. 补齐数据库唯一约束、事件表、状态迁移审计、金额/用户/币种校验和鉴权。
8. 前端/聚合查询明确展示“订单生成中、支付确认中、已关闭退款中、退款成功、退款异常”，避免把最终一致窗口误报为失败。

## 6. 必测用例清单

- 同一 `request_id` 并发请求 10 次，只扣一次库存、只增加一次限购、只生成一单。
- promotion Kafka 写入成功但客户端收到超时，不得补库存后仍建单造成超卖。
- 建单成功后写 ZSET 失败，DB 补扫仍能按时关单并补库存。
- 支付回调与超时任务并发执行 1,000 次，每次只能 PAID 或 CLOSED；CLOSED 且实际支付成功时必须恰有一个退款任务。
- pay 本地 SUCCESS 后 Kafka 暂时不可写，恢复后 outbox 必须最终把订单置 PAID 或在已关单时退款。
- order CLOSED 后补偿 Kafka 暂时不可写，恢复后库存必须最终且仅恢复一次。
- CancelTransaction 与 SUCCESS 回调并发，若渠道实收则一定进入退款。
- FAILED 后又收到 SUCCESS、重复 SUCCESS、乱序回调，都能按渠道事实正确收敛。
- 同一订单两条支付流水先后成功，只保留业务允许的一笔，其余每笔均唯一退款。
- 伪造价格、金额、币种、用户 ID、他人订单号均被拒绝。
- 一条非法 Kafka 消息进入 DLQ 后，后续正常消息继续消费。
- 退款调用超时、查询 RUNNING、查询 SUCCESS、永久 FAILED 分别按策略收敛并触发告警。

## 7. 总结

当前项目对最典型的“支付成功与订单超时同一瞬间”处理方向是正确的：order 通过条件更新保证只有一个终态获胜，迟到支付转退款，库存补偿也具备消费幂等。但是整个链路还没有达到资金系统所需的可靠性闭环。最重要的缺口是价格可信性、秒杀请求幂等、DB 与 Kafka 的原子可靠投递、取消后真实成功的处理、支付主动对账，以及真实可用的退款网关。上述 P0 项应在对外承载真实交易前完成。
